Distinction: malicious code (e.g. malicious evm-units crate, you could see the source) vs malware binaries (which we will focus on, since it requires reverse engineering)

* `arrayref` crate example: the build script downloaded a binary for your platform

What libraries are being used in rust malware?  The same crates everyone else is using.  As well as `obfstr`, which obfuscates the strings in a binary.  So you can't just run the `strings` command and see which filenames the binary has hardcoded.  Makes it very annoying for a reverse engineer!
* They gave a cool example of adding a breakpoint in the debugger -- showing how it is tricky and you only see the de-obfuscated code right before it is actually used.
* `obfstr` is dynamic based on memory addresses, so it is hard to actually find the string without... running the program

* Binary static analysis tools (IDA Pro, Ghidra, Binary Ninja, angr)
  * Finding the `fn main` in a static analysis code
  * Rust binaries have their own runtime code that runs before `fn main`, but these tools are used to C.  So they take you to where the C main would be, not the Rust main.
  * So we look for landmarks.  For example, the Rust stdlib runtime initialization code on Linux opens /dev/null a bunch
  * Eventually you get to a function pointer to a humungous function, it is `fn main()`

* Finding `strings` in a binary
  * CStrings end with a null terminator
  * Rust string slices have a pointer to the start of the string and a length

* Finding `panic!` location metadata in Rust binaries
  * When Rust panics, it gives you a nice message: "Panicked in file X, line Y, col Z"
  * That is stored in a struct in the binary, you can recover information about the source that way!
  * You can find out a lot about the author with these!  The path of the crate that might panic, you
    can find out exactly which crate versions, what directory they compiled in.
  * You can find out the version of the Rust stdlib they were using (and hence the Rust version too)
  * Rust malware developers could theoretically remove this, so you can't rely on it being there.

* library code similarity matching tools
  * but Rust binaries are quite inlined, so this doesn't work in those cases

* calling conventions
  * how you pass data from one function to another, which registers do you look in, etc.
  * Go has a calling convention guarantee when calling other Go code.  But Rust does not,
    it is not guaranteed.
  * An example of a reverse engineering tool finding an argument in a binary -- it found the
    arguments, but it didn't know about Rust string slices, so it looked like there was a
    gigantic string as one argument then a small integer.  But that was actually a single

### Layered Configuration and Safe Hot Reload in Rust
Hot reloading configuration in long-running services is often treated as a file-watching problem. In practice, most failures occur because configuration is mutated in place, partially applied, or insufficiently validated before entering runtime state.

This lightning talk presents a layered configuration model that makes safe hot reload a natural consequence of system design. Configuration flows through clearly separated stages: an operator-facing specification, parsing into an in-memory representation, structured validation, transformation into a runtime representation, and finally an immutable runtime snapshot used by the system.

Each stage produces a distinct representation with an explicit boundary and purpose. Validation happens before the runtime state exists. After validation, the runtime configuration is immutable and can be atomically replaced as a unit.

By separating specification from runtime and relying on immutable snapshots, hot reload becomes a matter of constructing a new validated configuration and swapping it in, rather than mutating global state. Rust’s type system and ownership model make these boundaries explicit and enforceable, reducing the risk of partial updates and inconsistent behavior.

The pattern applies broadly to long-running Rust services that need reliable configuration updates without restarts or shared mutable state.
